## 0. 结论摘要（TL;DR）

这个项目**功能密度已经很高**：混合检索（向量 + pg_trgm + RRF + LLM 重排）、语义缓存、多轮记忆增强、短查询改写、GraphRAG、双模式 3D 图谱、文档共享、SSE 流式、追问建议、检索调试面板——RAG 应用该有的"亮点"基本都有了，注释与文档质量在同类项目里属于上游水平。

问题不在"缺功能"，而在**三处结构性短板**：

| 短板 | 一句话 | 影响面 |
| :--- | :--- | :--- |
| **1. 服务边界不安全** | `ai-service` 完全无鉴权，且信任请求体里的 `userId` / `filePath` | 任意用户可读他人知识库、可让服务端读任意本地文件、可删任意文档索引 |
| **2. 索引链路是"黑盒"** | 索引 fire-and-forget、失败只写日志、没有 per-document 状态 | 用户看到"正在索引文档"后永远不知道成功没成功，`.doc` 这类必然失败的文件静默消失 |
| **3. 向量存储用 text 且无向量索引** | `document_chunks.embedding` 是 `text` 列，每次查询逐行 `::vector` 转型 | 无 ANN 索引、必然全表扫描；文档量上千后问答延迟会陡增 |

再叠加两个"迟早爆"的隐患：**双 TypeORM 主版本共存（1.1.0 + 0.3.31）**、**同库双份实体定义 + 无迁移方案**。

新亮点功能的高性价比方向不是再堆检索技巧，而是：**索引可观测与自愈 → 引用溯源到页 → RAG 评估看板 → 反馈闭环 → 成本看板**。这五个是把项目从"能跑的 Demo"变成"可交付产品"的分水岭。

### 1.2 问答链路（真实执行顺序）

```
前端 ChatPanel
  └─ fetch POST /chat/conversations/:id/messages  (SSE)
      └─ server ChatService.sendMessageStream
          ① 落库用户提问、刷新会话 updatedAt
          ② 取"最近 10 条"历史 ← ⚠️ 实际取到的是最旧 10 条（见 P1-1）
          ③ fetch POST ai-service /ai/ask/stream  (SSE，空闲 90s 超时)
              └─ AskService.askStream
                  ① 语义缓存查询（embed 问题 → 余弦 ≥ 0.95 直接复用）→ 命中则 onSources + 整段 onToken
                  ② 多轮记忆增强 contextualizeQuery（LLM 改写，串行）
                  ③ 短查询改写 rewriteQuery（≤4 字触发，LLM，串行）
                  ④ 向量路（pgvector cosine，LIMIT topK，minScore 绝对过滤）
                     + 关键词路（pg_trgm ILIKE，question/contextualized/rewritten 各一路）
                  ⑤ RRF 融合 → 每文件保留最优
                  ⑥ LLM 重排（只保留相关片段，RERANK_TOP_N）
                  ⑦ relativeSimilarity 分数校准（最强匹配固定 0.9）
                  ⑧ GraphRAG：纯 SQL 召回实体关系三元组注入上下文
                  ⑨ 并行：答案流式生成 ‖ 外部资料 JSON 生成
                  ⑩ 去重伪外部资料 → 写语义缓存 → 生成追问建议 → done
      └─ 透传 sources/token/done/error，落库完整回答
```

单次问答的模型调用成本：**最多 6 次 LLM + 2 次 Embedding**（contextualize、rewrite、rerank、answer、external、suggestions + 缓存 embed、检索 embed）。

## 2. 已落地能力盘点

**检索与问答（ai-service）**
- 混合检索：向量语义路 + pg_trgm 字面路（原始/记忆增强/改写三路）→ RRF(`k=60`) 融合 → 每文件去重 → LLM 重排
- 短碎片查询 LLM 改写（≤4 字符，如"彭"→"彭基良"）
- 多轮记忆增强（指代消解："它的优缺点呢"）
- 语义缓存（阈值 0.95，每用户上限 200 条，命中计数）
- 分数双轨：`score`（原始）+ `similarity`（校准后展示）
- GraphRAG：实体—关系—实体三元组纯 SQL 召回 + bigram 打分注入
- 伪外部资料去重（文件名匹配 + bigram 覆盖率 0.4）
- 追问建议（2~3 条），性能指标（检索/生成/总耗时）
- 检索调试面板：完整链路可视化（改写 → 多路召回 → 融合 → 保留）

**文档处理**
- 格式：PDF / DOCX / XLSX / XLS / CSV / MD / TXT（GBK/GB2312/UTF-16LE 编码探测）/ 图片 OCR（chi_sim+eng）
- 切片：`RecursiveCharacterTextSplitter`，1000/200 重叠；文件名前置一次以支持按名检索
- 批量 Embedding（BATCH_SIZE=10，适配豆包限制）
- 覆盖式重建（先删后插）+ 索引期间文档已删的竞态保护
- 孤儿分块过滤（`LEFT JOIN upload_files`）+ 删除文档同步清分块与图谱

**配置与运维**
- 用户级模型配置（OpenAI 兼容 / Anthropic 原生双协议），指纹缓存自动重建，改配置免重启
- 设置页可分别测试当前未保存的对话模型与向量模型配置；测试成功计入用量，不保存 API Key
- 向量模型变更自动全量重建索引 + 进度轮询（2s）+ 手动触发重索引
- 全局 JWT 守卫 + `@Public()` 放行白名单

**前端**
- SSE 流式问答（切换会话不中断后台生成、停止生成保留已生成内容）
- 引用角标 ↔ 来源项双向定位、来源片段关键词高亮、来源一键定位到文档列表/原文预览
- 文档在线预览（图片/PDF/Word/Excel/CSV/MD/TXT），无法解析时降级为下载
- 文件夹上传（File System Access API + webkitdirectory 回退）、同名查重、粘贴文本导入
- 会话/文档搜索过滤、批量删除、重命名、共享、会话导出 Markdown、消息点赞点踩
- 3D 知识图谱（力导向聚类、泛光特效、文档/实体双模式、实体节点联动文档预览）
- 深浅色主题（localStorage 持久化）

## 3. 风险与问题清单

### P0 · 安全（建议优先处理，都属于"部署到公网即出事"级别）

#### P0-1 `ai-service` 完全无鉴权，且信任请求体里的 `userId` / `filePath`

> **状态：✅ 已修复（2026-10-13）** — ai-service 只监听 `127.0.0.1`，新增 `X-Internal-Token` 内部共享密钥守卫（`internal-token.guard` + `assert-internal-token`），`filePath` 经 `assertPathInsideUploadRoot` 目录白名单校验；`DELETE /ai/document/:id` 纳入守卫。

- **证据**
  - `apps/ai-service/src/ai/ai.controller.ts:15` — `@Controller('ai')`，**无任何守卫**
  - `apps/ai-service/src/main.ts:12-19` — 只注册 `ValidationPipe`，无全局守卫
  - `apps/ai-service/src/ai/dto/ai.dto.ts:44-46` — `userId` 由调用方传入，服务端不做身份校验
  - `apps/ai-service/src/ai/dto/ai.dto.ts:24-27` — `filePath` 是任意绝对路径，无目录白名单
  - `apps/ai-service/src/ai/ai.controller.ts:28-33` — `DELETE /ai/document/:uploadFileId` 无归属校验
  - `apps/ai-service/src/ai/document-index.service.ts:168-174` — 未知扩展名直接按文本读取任意文件
- **影响（三个独立的攻击面）**
  1. **越权读**：`POST /ai/ask`（或 `/ai/ask/stream`）传任意 `userId` 即可检索该用户全部知识库内容。ID 是自增整数，可枚举。
  2. **任意文件读取（LFI）**：`POST /ai/index-document` 传 `filePath=C:\Windows\win.ini` 或 `/etc/passwd`，配合一个已存在的 `uploadFileId`（自增可猜），文件内容会被读入 `document_chunks`，再通过 `/ai/ask` 取回。**同时会先删后插该 `uploadFileId` 的原有分块，等于顺带破坏别人的索引。**
  3. **越权删**：`DELETE /ai/document/:id` 删除任意文档的全部分块与实体图谱。
- **建议**
  - 立即：`ai-service` 只监听 `127.0.0.1`（`app.listen(port, '127.0.0.1')`），并在部署层用网络策略禁止外部访问 3001。
  - 短期：加内部共享密钥守卫（`X-Internal-Token`）+ 校验 `filePath` 必须落在 `apps/server/uploads` 解析后的绝对路径前缀内。
  - 中期：`userId` 不再由请求体传入，改为 server 端签名/网关注入；或直接让 server 只暴露"检索"能力，答案生成仍走内部调用但带签名。

#### P0-2 JWT 密钥是公开的默认值

> **状态：✅ 已修复（2026-10-13）** — 新增 `apps/server/src/auth/assert-secrets.ts`，启动时校验 `JWT_SECRET` 非默认值且长度 ≥32，否则拒绝启动（fail-fast）。

- **证据**：`.env:14` → `JWT_SECRET=your_secret_key`；`apps/server/src/config/configuration.ts:18` 同款默认值；`README.md:74` 也把它写成默认值
- **影响**：任何人可用公开字符串伪造 JWT，指定任意 `sub` 即完全接管账号（含读全部文档、调用模型花用户的钱）
- **建议**：启动时校验 `JWT_SECRET` 非默认值且长度 ≥32，否则**拒绝启动**（fail-fast），而不是静默用弱密钥；同时补 refresh token / 支持主动吊销（`tokenVersion` 字段）

#### P0-3 用户 API Key 明文落库

> **状态：✅ 已修复（2026-10-14）** — `ai_settings` 三个 API Key 列使用 AES-256-GCM TypeORM transformer 加密；服务启动时把历史明文批量迁移为密文。新增 `ENV_ENCRYPTION_KEY`，本地 `.env` 已生成独立密钥且未提交。

- **证据**：`apps/server/src/settings/ai-settings.entity.ts:27-28`、`37-38`、`47-48`（`openaiApiKey` / `anthropicApiKey` / `embeddingApiKey` 均为 `varchar` 明文）；`apps/ai-service/src/entities/ai-settings.entity.ts` 同款
- **影响**：一次数据库备份泄漏 = 所有用户的模型 Key 泄漏；且 Key 会随 `.env` 的 `OPENAI_API_KEY` 一起被当成"回显默认值"泄漏给任何登录用户（`resolveView` 只隐藏"是否已配置"，但如果用户没配过，前端看到的是环境级共享 Key 的存在性）
- **建议**：AES-256-GCM 加密（主密钥来自 `ENV_ENCRYPTION_KEY` 或 KMS），存 `ciphertext + iv + keyVersion`；支持"轮换主密钥"；日志与异常里永不打印 Key

#### P0-4 无登录限流 / 无问答配额

> **状态：✅ 已修复（2026-10-13，部分）** — 接入 `@nestjs/throttler` 全局限流（默认 120 次/分钟/用户），问答接口单独 `@Throttle({ limit: 20, ttl: 60s })`。登录按 IP 限速未单独做（可后续按 P0-4 原建议补）。

- **证据**：`apps/server/src/auth/auth.service.ts:40-53`（登录无失败计数）；`apps/server/src/auth/dto/register.dto.ts:13-15`（密码仅长度 6~72，无复杂度）；全局无 `@nestjs/throttler`
- **影响**：登录口令爆破；注册接口刷号；调用 `/chat/.../messages` 可无限消耗模型额度（每次最多 6 次 LLM 调用），是**直接烧钱**的 DoS
- **建议**：接入 `@nestjs/throttler`（登录按 IP+用户名双维度限速、问答按用户限速）；增加每用户日/月 token 配额与超限降级（走缓存或拒答）

#### P0-5 上传只校验扩展名（不校验文件头），且 `/uploads` 直连静态托管

- **证据**
  - `apps/server/src/upload/upload.storage.ts:51-63` — `allowExtension` 仅比对扩展名，不校验 MIME 与 magic number；头像路径额外查了 `mimetype`（`:74-79`），文档路径**连 MIME 都不查**
  - `apps/server/src/main.ts:15` — `express.static` 裸托管，无 `X-Content-Type-Options: nosniff`、无 CSP
  - `apps/server/src/main.ts:23-26` — CORS 硬编码 `http://localhost:5173`，非配置项
- **影响（实事求是地说，直接 XSS 风险不高，但另外两个影响是真实的）**
  1. `express.static` 按扩展名决定 `Content-Type`，所以"把 HTML 改名成 `.jpg`"不会被浏览器当 HTML 执行 —— 存储型 XSS 不是主要风险，但**缺少 `nosniff` 与 CSP 属于纵深防御缺失**，一旦未来放开格式白名单（如新增 `.svg`、`.html` 导入）会立刻变成真漏洞。
  2. 任意二进制文件只要改成白名单扩展名就能进入索引流水线 → 触发无意义的 OCR/解析，**是廉价的服务端资源消耗面**（配合 P2-2 的 120s 超时与单次全量 `save()`，可被用来制造长时间占用）。
  3. 文档类型与内容不符时，索引失败（P1-3）对用户完全不可见，等于白等。
- **建议**：用 `file-type` 做文件头校验并与扩展名交叉验证；`originalName` 落库前过滤控制字符；静态目录加 `nosniff` + CSP sandbox；CORS 改为 `CORS_ORIGIN` 配置项（支持逗号分隔多源）

### P1 · 功能正确性（用户可直接感知的 Bug）

#### P1-1 多轮对话"最近 10 条历史"取到的是**最旧 10 条**

> **状态：✅ 已修复（2026-10-13）** — `chat.service.ts` 改用 `order: { id: 'DESC' }, take: 10` 再 `reverse()`，取到真正的最近 10 条。

- **证据**：`apps/server/src/chat/chat.service.ts:166-170`
  ```ts
  const history = await this.messagesRepository.find({
    where: { conversationId: conversation.id },
    order: { id: 'ASC' },
    take: 10,           // ← ORDER BY id ASC LIMIT 10 = 最早的 10 条
  });
  ```
- **影响**：会话超过 10 条消息后，传给 ai-service 的历史永远是对话开头。第 2 条就依赖的"多轮记忆增强"与"指代消解"实际上全部失效——`contextualizeQuery` 拿到的是一堆无关的早期内容，反而可能把查询改写歪。
- **修复**：`order: { id: 'DESC' }, take: 10` 后再 `reverse()`；或 `find` 后 `slice(-10)`。

#### P1-2 粘贴文本导入超过约 100KB 必然失败（413）

> **状态：✅ 已修复（2026-10-13）** — `main.ts` 用 `NestFactory.create(AppModule, { bodyParser: false })` + 手动 `json({ limit: '2mb' })`，与前端提示的 20 万字符上限对齐。

- **证据**：`apps/server/src/upload/upload.controller.ts:63-75` 允许最多 20 万字符；`apps/web/src/stores/chat.ts:533-536` 前端也按 20 万字符校验并提示；但 `apps/server/src/main.ts:12-27` **没有配置 bodyParser limit**，Nest 默认 JSON 限制 `100kb`
- **影响**：约 3.4 万汉字（或 10 万 ASCII 字符）以上的粘贴内容直接被 413 拒绝，用户看到"导入失败"，与提示的"最多 20 万字符"完全矛盾
- **修复**：`NestFactory.create(AppModule, { bodyParser: false })` 后手动 `app.use(json({ limit: '2mb' }))`；或统一把上限降到 100KB 以下并同步前端提示

#### P1-3 文档索引状态完全缺失，"索引失败"对用户不可见

- **证据**
  - `apps/web/src/api/upload.ts:16` — 前端类型声明了 `indexed: boolean`，但后端**从不返回该字段**
  - `apps/server/src/upload/upload.service.ts:99-102` / `133-136` — `setImmediate` fire-and-forget
  - `apps/server/src/upload/upload.service.ts:311-318` — 失败仅 `logger.warn`
  - `apps/server/src/upload/upload.storage.ts:31` 允许 `.doc`，但 `apps/ai-service/src/ai/document-index.service.ts:160-161` 对 `.doc` 直接抛 `BadRequestException` → **必然静默失败**
  - 扫描版 PDF（pdf-parse 抽不出文本）→ `文档不包含可索引内容` → 同样静默失败
- **影响**：用户上传后只看到"上传成功，正在索引文档"，之后文档列表毫无差别——**一个永远检索不到的文档看起来和一个正常文档完全一样**。这是当前最伤体验的缺陷。

### P2 · 性能与规模化（文档量/用户量上来后暴露）

#### P2-1 向量以 `text` 存储，无 ANN 索引 → 必然全表扫描

- **证据**
  - `apps/ai-service/src/entities/document-chunk.entity.ts:42-46` — `embedding` 声明为 `type: 'text'` + 自定义 transformer
  - `apps/ai-service/src/ai/ask.service.ts:707-716` — `c.embedding::vector <=> $1::vector ... LIMIT topK`
  - `apps/ai-service/src/services/database-initialization.service.ts:21-23` — 只创建了 `content` 的 trgm GIN 索引，**没有任何 HNSW/IVFFlat 索引**（全项目 grep 无 `hnsw|ivfflat`）
  - `apps/server/src/stats/stats.service.ts:138-145` — `AVG(c.embedding::vector)` 同样逐行 cast
- **影响**
  - `::vector` 是表达式，**索引无法命中**，每次检索都要对全表做 float 距离计算（10 万 chunk ≈ 上亿次浮点运算 + 全表 IO）
  - text 存储体积约为 `vector` 类型的 2~4 倍
  - 切换 Embedding 模型（向量维度变化）时，重建过程中新旧 chunk 维度混杂，`::vector` 比较会直接抛 `different vector dimensions` —— **重建期间问答整体 500**
- **修复（性能专项，收益最大的一条）**
  1. `embedding` 改成真正的 `vector(N)` 列，写入即转型；`metadata` 里记录 `embeddingModel` + `dim`.
  2. 建 HNSW 索引：`CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)`。
  3. 检索 SQL 去掉 `::vector` cast，改成 `WHERE ... ORDER BY embedding <=> $1::vector LIMIT k`。
  4. 维度治理：`ai_settings` 增加 `embeddingDim`；重建时先写入新表/新分区再原子切换，避免中途混合维度。

#### P2-2 一次性 `save()` 全部 chunk → 大文档可能撞 PostgreSQL 参数上限

- **证据**：`apps/ai-service/src/ai/document-index.service.ts:97-113`（单个 `save(chunks.map(...))`）；切片参数 `CHUNK_SIZE=1000 / CHUNK_OVERLAP=200`（`:24-27`）
- **影响**：20MB 上限的文本文件 ≈ 2.5 万个 chunk → 单条 INSERT 绑定参数 ≈ 10 万个，**超过 PostgreSQL 的 65535 参数上限而直接报错**；即使没超限，几百 MB 的 SQL 与内存峰值也很危险。叠加 `apps/server/src/upload/upload.service.ts:293` 的 **120s** 索引超时，大文件基本注定失败且静默
- **修复**：按 500~1000 行分批 INSERT（`save(chunk, { chunk: 500 })` 或分片调用）；索引超时改为"提交任务 + 轮询/回调"模式；对超长文档先降采样或提示

#### P2-3 单次问答最多 6 次 LLM + 2 次 Embedding，且部分可合并

- **证据**：`apps/ai-service/src/ai/ask.service.ts:693-695`（contextualize → rewrite 串行）、`:230`（`generateSuggestions` 在 `done` 之前 await）、`:217-220`（answer ‖ external，已并行）
- **影响**：首字延迟与成本双高；`done` 事件被 suggestions 阻塞 → 前端"生成中"状态（发送按钮变停止按钮）多停留 1~3 秒
- **修复**
  - 合并 contextualize + rewrite 为一次 LLM 调用（都是"查询改写"，一次输出即可）
  - suggestions 改为独立 SSE 事件（`suggestions`）在 `done` 之后异步推送
  - 重排可降级为更便宜的本地交叉编码器或阈值前置，只有候选多时才调 LLM

#### P2-4 文档图谱 O(n²) 在 Node 侧全量重算

- **证据**：`apps/server/src/stats/stats.service.ts:162-177`（双重循环求两两余弦）
- **影响**：500 个文档 → 12.5 万次 1536 维余弦（≈2 亿次乘加），每次刷新图表都重算，且结果不落库
- **修复**：改为 SQL 侧聚合（pgvector 的 `vector` 聚合 + 单条 `cross join` 查询）或预计算缓存（文档变更时增量更新近邻）

#### P2-5 索引/实体抽取是进程内 fire-and-forget

- **证据**：`apps/server/src/upload/upload.service.ts:99-102`；`apps/ai-service/src/ai/document-index.service.ts:116-120`（`void this.entityExtraction.rebuildForDocument(...)`）
- **影响**：服务重启 → 正在索引的文档永久停留在"没索引"状态（且用户看不到）；无重试、无并发控制、无优先级；一次批量上传 100 个文件会同时发起 100 个 Embedding 循环
- **修复**：引入轻量持久化队列（`pg-boss` 复用现有 Postgres，零新增中间件）或 BullMQ；失败自动重试 + 指数退避 + 死信；并发上限可配

#### P2-6 模型实例缓存无上限

- **证据**：`apps/ai-service/src/ai/openai-model.provider.ts:34-35`（两个 `Map<userId, ...>`，永不清理）
- **影响**：多用户长期运行内存单调增长；每个缓存项持有 HTTP client 与配置
- **修复**：LRU 上限（如 500）+ 空闲过期；或用 `lru-cache`

#### P2-7 `.env` 默认值与两处常量三处重复

- **证据**：默认值同时存在于 `apps/server/src/config/configuration.ts:26-39`、`apps/server/src/settings/settings.service.ts:228-250`、`apps/ai-service/src/config/configuration.ts:15-28`、`apps/ai-service/src/settings/user-settings.service.ts:65-89`，注释还写着"与 xx 保持一致"
- **影响**：改一个默认值要改四处，漏改就出现"设置页显示 A、实际生效 B"的诡异现象
- **修复**：把默认值抽到 `packages/shared`（或新增 `packages/config`）单一来源

## 4. 亮点功能建议

> 筛选标准：(1) 直接解决上面某个 P0/P1/P2 问题，(2) 用户能立刻感知价值，(3) 复用现有技术栈与数据结构，不引入重资产。
> 每条给出：为什么是亮点 / 实现要点 / 工作量 / 依赖。

### ★ 亮点 1：文档索引流水线可视化 + 自愈（Index Pipeline & Self-healing）

> **实现状态：✅ 已完成（2026-10-13）**
> 落地：upload_files 增加 indexStatus/chunkCount/indexedAt/indexError/errorKind/indexAttempts/embeddingModel/embeddingDim 字段；上传后状态机 pending→running→done/failed；失败指数退避自动重试 3 次（10s/30s/60s），仍失败标记 failed 并分类错误原因；新增 POST /upload/document/:id/reindex 手动重试（仅所有者）；前端文档列表显示状态徽标（转圈/绿勾/红叉+悬浮原因）、失败聚合条「N 个文档索引失败，全部重试」、单文档点击红叉重试、上传后轮询索引状态；.doc 上传时报错「请另存为 .docx」；ai-service 索引成功返回 chunk 数 + embeddingModel/embeddingDim，server 据此写回 done。

**为什么是亮点**：直接消灭 P1-3、P2-5。把"黑盒异步"变成"可见、可重试、可告警"。这是当前用户最先撞到、最伤信任的缺陷，做完立刻能演示。

**实现要点**
1. `upload_files` 加字段：`indexStatus(pending|running|done|failed|skipped)`、`chunkCount`、`indexedAt`、`indexError`、`indexAttempts`、`embeddingModel`、`embeddingDim`。
2. 引入 `pg-boss`（复用现有 PostgreSQL，零新增中间件）：上传后入队；worker 并发可配（默认 2~3）；失败指数退避重试 3 次后进死信。
3. ai-service 索引完成后回调 `PATCH /internal/documents/:id/index-status`（带内部签名，顺手解决 P0-1 的密钥守卫雏形）。
4. 前端文档列表：状态徽标（转圈/绿勾/红叉+悬浮原因）、顶部"N 个文档索引失败，点击重试"聚合条、单文档"重新索引"菜单项。
5. 前置拦截必然失败的输入：`.doc` 直接提示"请另存为 .docx"；扫描版 PDF 检测到抽取文本为 0 页时，提示"该 PDF 可能是扫描件，建议改用图片上传（走 OCR）"。

**工作量**：2~4 天（含 pg-boss 接入）。**风险**：低。

### ★ 亮点 2：引用溯源到"页 / 段落 / 原句"（Chunk Provenance & 原文定位）

**为什么是亮点**：RAG 最难取信用户的就是"你这句话从哪来的"。现在只能关键词高亮（还要降级拆 2 字窗口），做到"点引用 → PDF 跳到第 7 页并高亮该句"是质变。

**实现要点**
1. 索引时按格式记录定位信息写入 `metadata`：
   - PDF：`page`（pdf-parse 按页循环取文本，逐页切片）+ `charStart/charEnd`
   - DOCX：`headingPath`（mammoth 的 `convertToHtml` 带标题层级，或按段落序号）
   - XLSX：`sheet` + `rowRange`（现已标注工作表名，补行号即可）
   - 图片 OCR：`bbox`（tesseract 支持词级坐标）
2. `RetrievedChunk.metadata` 扩展（`packages/shared` 加类型），SSE `sources` 直接携带。
3. 前端 PDF 预览换 `pdf.js`，按 `page` 跳转 + 按 `charStart/charEnd` 或关键词精确定位；Word/Excel 用段落/行号定位；图片用 bbox 画高亮框。
4. 来源卡片显示"第 7 页 · 第 3 段"而不是干巴巴的相关度。

**工作量**：3~5 天（PDF 分页抽取最费力，其余格式便宜）。**依赖**：`pdfjs-dist`（前端，可懒加载）。

### ★ 亮点 3：RAG 评估与回归看板（Eval Harness）

> **实现状态：✅ 已完成（2026-10-13）**
> 落地：新增 eval_sets/eval_cases/eval_runs/eval_results 四张表；支持评估集/用例 CRUD、运行/历史/明细；新增 `POST /eval/sets/:id/compare`，同一评估集按两套独立参数依次运行并分别落库；前端可编辑 topK/keywordTopK/minScore/rerankTopN、对比指标并查看 A/B 各自逐题明细。

**为什么是亮点**：这是把项目从"手工调参"升级为"可量化迭代"的功能，也是最能证明工程成熟度的一点。当前 `retrieve`/`rerank` 的任何改动都无法自证"变好了"——README 只能写"请人工核对"。同时它顺手解决 P3-4。

**实现要点**
1. 新表 `eval_sets`（问题集）、`eval_cases`（问题 + 期望命中的 `uploadFileId`/关键片段关键词 + 期望答案要点）、`eval_runs`（参数快照 + 指标）、`eval_results`（逐题明细）。
2. 指标：`recall@k`（期望文档是否进 kept）、`MRR`、`无答率`、`引用准确率`（引用片段是否含期望关键词）、`平均检索耗时`、`平均生成耗时`、`缓存命中率`。全部复用现有 `retrieve()`（可传 `trace`），**不需要真的生成答案**即可跑检索类指标（省钱、秒级）。
3. 用现有 `debugRetrieve` 的 trace 结构输出"哪一步丢了正确片段"（向量路没召回？关键词路没命中？还是被 rerank 剔除了？）——把 Debug 面板升级成"带标准答案的 Debug"。
4. 一键 A/B：保存两套检索参数（如 `minScore 0.3 vs 0.5`、`RRF_K 60 vs 10`）跑同一问题集，出对比表。
5. 把 README 的三个"核心不变量"变成 3 个自动化用例，挂到 CI。

**工作量**：4~6 天。**亮点加成**：可以做成"点一下，自动扫全网参数组合，给出最优 topK/minScore/rerankTopN"——几乎是论文级的演示效果。

### ★ 亮点 4：反馈驱动的自优化闭环（Feedback → Badcase → 重排权重）

> **实现状态：✅ 已完成（2026-10-13）**
> 落地：messages 增加 feedbackReason/feedbackSourceIndex 字段；PATCH /chat/messages/:id/feedback 支持 reason 与 sourceIndex（点踩写原因、点赞记哪条引用有用）；点踩自动把该问题 + 第一条知识库来源 + 期望关键词写入「自动收集的 Badcase」评估集（与亮点 3 打通）；前端消息反馈弹对话框（点踩选原因、点赞选来源）；新增 GET /feedback/dashboard（热门点踩问题 Top10、按文档统计被点踩引用来源、点踩原因分布）+ 前端「反馈看板」页。

> **未做（后续可选）**：在线学习（对 positive chunk 的 RRF 加权 1/(k+rank+1)·(1+α·posRate)）与阈值自调（按点踩率/无答率自动调 minScore/rerankTopN）——这两条属原实现要点第 3/4 条，涉及权重开关与回滚，留作增强项。

**为什么是亮点**：项目已经有 `messages.feedback`（like/dislike）和引用来源落库，但**这些信号目前只用于显示图标**，是纯粹的浪费。把它闭合起来，系统会越用越准。

**实现要点**
1. 点踩时弹"哪里不对"：引用无关 / 答案不全 / 未用知识库 / 答非所问 / 其他（写入 `feedback_reason`）；点赞时记录"哪条引用有用"。
2. 自动生成 badcase 库：点踩的问题 + 当时 kept 片段 + trace → 直接进"评估问题集"（与亮点 3 天然打通）。
3. 轻量在线学习：对"被点赞引用的 chunk"在其 `metadata` 打正例标记，检索时对正例做 RRF 加权（`1/(k+rank+1) * (1 + α·posRate)`），α 可配、可开关、可回滚。
4. 阈值自调：按点踩率与"无答率"自动建议/调整 `minScore`、`rerankTopN`（配合亮点 3 验证）。
5. 看板：热门点踩问题 Top10、按文档统计"最常被点踩的引用来源" → 直接指出**哪些文档内容质量差**。

**工作量**：3~4 天。**风险**：中（权重调整需要有开关与回滚，避免越调越差）。

### ★ 亮点 5：成本与用量看板（Token / 费用 / 配额）

> **实现状态：✅ 已完成（2026-10-14）**
> 落地：`ai_usage_events` 记录模型实际 token、单价配置产生的 USD 费用估算及 usage 来源；覆盖问答、Embedding、文档索引和实体抽取；`GET /usage` 展示按天/类型/模型费用、未计价模型、未返回 Token 的调用与旧估算记录。设置页支持每日/月 Token 软配额，达到后关闭改写、重排、外部资料、追问建议和实体抽取，保留检索及核心问答；精确模型单价通过 `AI_MODEL_PRICING` 配置，未配置不估价。

**为什么是亮点**：多用户 + 每次最多 6 次 LLM 调用 + 语义缓存 = 成本结构完全不可见。这既是产品能力（配额、套餐）也是护城河（语义缓存命中率能直接换算成省了多少钱，让"缓存"这个功能第一次有了可量化的价值证明）。

**实现要点**
1. 新表 `ai_usage_events`：`userId / conversationId / messageId / provider / model / kind(contextualize|rewrite|rerank|answer|external|suggestions|embedding|extraction) / promptTokens / completionTokens / latencyMs / cached / createdAt`。
2. `openai-model.provider` 统一包一层计量装饰器，所有调用自动记录（Anthropic 分支同样处理）。
3. 看板：按天/用户/模型聚合 token 与估算费用；语义缓存命中率与"节省的调用次数/费用"；`kind` 维度排行直接暴露"哪一步最烧钱"（大概率是 suggestions 与 external，可据此砍掉或降级）。
4. 配额与降级：日/月上限可配，超限时自动关闭非必要调用（suggestions → external → rerank 依次降级），核心问答仍可用。
5. 顺手暴露 Prometheus 指标（P3-7）。

**工作量**：3~4 天。**亮点加成**："本次回答消耗 1,842 tokens / ¥0.0031"直接显示在回答下方，用户对成本的感知会彻底改变。

## 6. 一句话总评

**产品功能已经领先于工程质量。** 检索链路的精巧程度（三路召回 + RRF + 校准 + 图谱注入 + 缓存）超过多数同类项目，但支撑它的地基还有三处裂缝：**服务边界无鉴权、索引过程不可观测、向量存储未按向量优化**。好消息是这三处都不需要重写架构——都在 1~2 周内可闭环，且闭环之后，`引用溯源` 与 `评估看板` 这两个真正能拉开差距的亮点功能才有坚实的地基可以长上去。
